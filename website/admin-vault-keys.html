Admin - Vault Relayer Keys

The ETH/USDC vault release relay (contracts/CreditChainVault.sol's release()) needs a funded account to pay gas - see api/vault_release_relay.go for the server-side version of this same relay. This page is the deliberate alternative: the key is pasted in here, stored only in this browser's localStorage, and every release is signed and broadcast entirely client-side (the exact same self-custodial primitives every Send flow on this site already uses - website/js/vendor/eth-tx.js). The key is never sent to the server in any form.

Tradeoff: this only runs while this page is open in a tab (a setInterval loop, stopped the moment the tab closes) - not a 24/7 background service like the server-side relay would be. Leave it open in a pinned tab for continuous coverage, or just open it periodically to catch up; a release approval stays queued (and safely re-triggerable - the contract's usedReleaseIds rejects any duplicate) until something relays it.

The relayer key itself carries zero authority over which releases are valid - the contract independently verifies each bridge-validator signature on-chain via ecrecover. This key only pays gas and assembles already-authorized calldata.

Register as Bridge Validator

The vault release relay only works once at least one bridge validator is registered - see api/bridge_validator.go's HandleBridgeValidatorRegister. Both Ethereum and Bitcoin sign on the same secp256k1 curve, so the same key saved above (Testnet box) can supply both the EthSigningAddress and BtcPublicKeyHex this registration needs - derived here, entirely client-side, never sent anywhere until you click Register.

This submits a TxBridgeValidatorRegister transaction signed by your currently logged-in CreditChain wallet (the same sign-in every other page on this site uses) - it only succeeds if that wallet's address is listed in the server's BRIDGE_VALIDATOR_ADDRESSES.

Auto-Bridge Relayer Fees (ETH)

The relayer's own address also collects ETH_CCC1 as its cut of every ETH/USDC release's fee (see RELAYER_FEE_RECIPIENT_ETH_ADDRESS in api/vault_fee.go) - but that's a CreditChain-side balance, not real ETH, so it never refills the gas tank on its own. This checks that balance against roughly 10 releases' worth (computed live from the current per-release fee estimate, not a literal transaction counter - there's no cheap way to count discrete fee events from the browser, and a value-based threshold serves the same purpose), and once past it, unvaults the whole balance back to real ETH sent to the relayer's own address - closing the loop.

These fees are collected by RELAYER_FEE_RECIPIENT_ETH_ADDRESS - a real CreditChain wallet's own self-custodial ETH address, a different credential from the relayer key above (the relayer key may have no CreditChain wallet behind it at all - e.g. an exchange-exported key - so it can never sign an unvault itself; it's only used here to know the release destination). This ticks against whichever CreditChain wallet is currently logged into this browser and only works if that's the specific wallet configured as the fee recipient - any other wallet just shows a 0 balance and never bridges anything.

Lock Attestation (ETH / USDC deposits)

Without this running, a real deposit to the vault contract just sits there forever - nothing else independently confirms it happened, so ETH_CCC1/USDC_CCC1 never mints. This scans the real chain directly (a public RPC, not a CreditChain node) for Locked events and submits TxVaultLockAttest, signed by your currently logged-in CreditChain wallet - no relayer key needed for this part.

Lock Attestation (BTC deposits)

BTC's equivalent of the card above - scans the vault's shared P2WSH address via a public Esplora API (blockstream.info) for confirmed deposits carrying a valid OP_RETURN depositor memo, and submits TxVaultLockAttest the same way, signed by your currently logged-in CreditChain wallet. Without this running, BTC_CCC1 never mints either.

Release Approvals (ETH / USDC / BTC)

Withdrawals sit here until a bridge validator signs off. For ETH/USDC, "Sign & Approve" computes the release's exact digest (mirroring contracts/CreditChainVault.sol's release()) and signs it with the relayer key saved above. For BTC, it instead reconstructs the exact unsigned P2WSH multisig release transaction (same UTXO selection and fee as the server-side relay) and produces a real Bitcoin signature over it - a materially different scheme, same relayer key. Either way the signature is submitted as a TxVaultReleaseApprove transaction signed by your currently logged-in CreditChain wallet - same two-separate-credentials split as Bridge Validator registration above.

Update Vault Validators (one-off governance action)

contracts/CreditChainVault.sol has its own separate, on-chain validator list - registering a validator in this app's own backend (above) does NOT add it here too. This is a full REPLACEMENT of the real list (not an addition), so include every address that should remain a validator, not just the new one. Requires a real threshold-signed digest from the CURRENT validator set - sign with the relayer key saved above (must belong to a CURRENT validator), then this node relays the real transaction using the funded relayer account, so your signing key never needs its own ETH for gas.


Allow/Disallow a Vault Deposit Token (one-off governance action)

Only tokens in the vault contract's own allowedTokens map can be deposited via depositERC20() - e.g. Lido's real stETH (0xae7ab96520DE3A18E5e111B5EaAb095312D7fE84 on mainnet) for the ETH liquid-staking feature. Same threshold-signed relay pattern as the validator update above.


Set Per-Depositor Caps (one-off governance action)

perDepositorCapUsdc compares every depositERC20() call's RAW deposited amount against this cap, regardless of that token's own decimals - it cannot correctly evaluate an 18-decimal token like stETH (any real deposit would trivially exceed a 6-decimal-USDC-scaled cap). Set to 0 to disable a cap entirely. This applies to every depositor and every allowed ERC20 token, not just one.
